SQLite: matching attribution to release evidence

Google attributed discovery of CVE-2025-6965 to Big Sleep, with input from its threat intelligence team. SQLite’s release history documents the upstream correction in version 3.50.2. Google’s announcement supports the attribution and SQLite’s release record supports the fix. Downstream products can ship the library or its correction on a different schedule.

Firefox: a collaborative review and disclosure

Mozilla reports that collaboration with Anthropic using Claude Opus 4.6 led to fixes for 22 security-sensitive bugs in Firefox 148. Its security advisory credits named researchers using Claude on individual entries. The vendor’s campaign count covers its stated review scope. A comparison between tools would require equivalent coverage, review effort and counting rules.

A released fix and an installed update

A vendor advisory can establish a fixed release for a particular product or branch. Whether a user is protected also depends on the version or downstream update they have installed. The catalog records remediation at the scope supported by the cited source.

What should a disclosure establish?

Look for the source that credits the model, the researchers or vendor who confirmed the report, and the advisory that documents the fix. These examples describe public vendor and researcher evidence. They support conclusions about the reported cases and releases within that scope.

How to interpret the evidence

What does AI attribution establish?

A report can credit a model and still describe work by human researchers. In the Firefox case, Mozilla says its engineers assessed the findings and landed fixes before the release. The sentence that credits the reporting team and the tool records how an issue was reported. The maintainer’s statement records a different step in the chain.

When comparing AI-assisted reports, check what the vendor confirmed and which findings received identifiers. Counts of initial suggestions, confirmed issues and published advisories measure different things. A published campaign total alone cannot reveal the rate of false positives or the effort spent on triage.

Read Mozilla’s account of validation and fixes

How do you read the evidence for a fix?

A CVE identifier names a publicly tracked issue. A vendor advisory can identify the affected product and the release containing the correction. In the Firefox 148 advisory, the fixed release appears in the advisory header, while reporter attribution appears against individual findings. This lets readers verify who was credited and what update was published.

A database library may also appear inside a separate product. The version that fixes the upstream library and the version that fixes the downstream product can differ. Use the advisory for the product you actually run when checking the update.

Read the Firefox 148 security advisory

What is the patch gap?

The patch gap is the interval between the appearance of a correction in code and its broad deployment. A software vendor can document the correction while some installations still run a prior build. The release, distribution and local installation each have their own evidence.

For a practical check, identify the product and installed version, then compare them with the vendor’s update notice. A package may receive a backported correction while keeping an older base version. Consult the distribution’s records for that package instead of inferring protection from an upstream version number alone.

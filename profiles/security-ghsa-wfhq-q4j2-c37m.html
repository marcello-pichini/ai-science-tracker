filelock SoftReadWriteLock can follow a substituted lock tree and write outside its directory

filelock Python SoftReadWriteLock and AsyncSoftReadWriteLock · AI involvement attributed to Anthropic OSS Scanner; exact model/version not identified for this finding

Finding and attribution

After a lock object validates its .rw tree once, another local account with write access to the parent can replace a nested gen or holders directory with a symlink. Later lock operations then create, replace, or delete the lock user’s own protocol files under another path, including a private Git repository. The advisory demonstrates replacement of .git/HEAD causing git status to fail. This requires a long-lived lock object and a writable shared parent; in a sticky directory such as /tmp, the attacker must plant the lock tree before the victim first acquires it. The documented reproducer ran on Linux; equivalent path behavior is described for POSIX and Windows junctions.

What to update · filelock Python SoftReadWriteLock and AsyncSoftReadWriteLock

Affected versions not confirmed in this summary.

Remediation note: Fixed in filelock 4.2.1. The advisory recommends protecting every ancestor of the lock path from replacement by another account; a sticky shared parent can suffice if the lock tree was not planted beforehand. Deployment status is not checked.
